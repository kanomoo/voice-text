## 2. สรุปสาระสำคัญ (Executive Summary)

บทเรียนในคาบนี้เป็นการปูพื้นฐานและเจาะลึกการสร้าง **Use Case Diagram** ในกระบวนการวิเคราะห์ความต้องการ (Requirement Analysis) ของวงจรการพัฒนาซอฟต์แวร์ (SDLC) โดยมีสาระสำคัญเชิงทฤษฎีและการประยุกต์ใช้ดังนี้:

### 2.1 วัตถุประสงค์และบทบาทของ Use Case Diagram
- **สื่อกลางระหว่าง Dev และ User:** เป็นไดอะแกรมระดับ High-level ตัวเดียวที่ผู้ใช้งาน (User / Customer) ที่ไม่มีความรู้ด้านคอมพิวเตอร์หรือโค้ดดิ้งสามารถอ่านเข้าใจได้ทันที โดยไม่มีตรรกะเชิงเทคนิค (No Algorithm, No Code, No Variables, No Database Schema)
- **แสดง Functional Requirements:** ระบุภาพรวมว่าระบบทำหน้าที่อะไรได้บ้าง (What the system does) โดยไม่ลงลึกว่าระบบทำงานข้างในอย่างไร (How it works internally)
- **สร้าง Traceability (ความสามารถในการสืบย้อน):** เชื่อมโยงรหัสความต้องการ (Requirement ID เช่น `001`, `002`) เข้ากับ User Story, Design Component, Source Code ไปจนถึง Test Case เพื่อยืนยันว่าฟังก์ชันทุกตัวสามารถทดสอบและส่งมอบได้จริง

### 2.2 สี่องค์ประกอบหลักของ Use Case Diagram (Elements)
1. **Actor (ผู้กระทำ / บทบาท):**
   - **สัญลักษณ์:** รูปคนกิ่งไม้ (Stickman / Stick figure) ห้ามวาดหน้าตา ผม หรือเสื้อผ้า
   - **กฎเหล็ก:** Actor คือ **บทบาท (Role)** ไม่ใช่บุคคลเจาะจง (ห้ามใช้ชื่อคน เช่น "อาจารย์สมชาย" หรือคำกว้างเกินไปอย่าง "คน", "User 1")
   - **ประเภท Actor:**
     - **Human Actor:** มนุษย์ผู้ใช้งาน เช่น `Bank Customer`, `Student`, `Instructor`, `Staff`
     - **System Actor (External System):** ระบบภายนอกที่ระบบของเราต้องติดต่อสื่อสารด้วย เช่น `Payment Gateway`, `Email Service`, `Bank System`, เครือข่ายโทรคมนาคม
     - **Primary Actor:** ผู้เริ่มต้นส่งคำสั่งเพื่อบรรลุเป้าหมาย เช่น ลูกค้าสั่งซื้อสินค้า
     - **Supporting Actor:** ผู้หรือระบบที่เข้ามาสนับสนุนให้ Use Case นั้นสำเร็จ เช่น เจ้าหน้าที่ทะเบียน หรือระบบส่งอีเมลยืนยัน
   - **ข้อควรระวัง:** ส่วนประกอบภายในระบบ เช่น Database, Web Server, Mobile App **ห้ามใส่เป็น Actor เด็ดขาด**
2. **Use Case (หน้าที่ / ฟังก์ชันการทำงาน):**
   - **สัญลักษณ์:** รูปวงรี (Oval) ต้องเป็นวงรีเท่านั้น ห้ามวาดเป็นสี่เหลี่ยมหรือวงกลม
   - **กฎการตั้งชื่อ:** ต้องขึ้นต้นด้วย **คำกริยา + กรรม/คำนาม (Verb + Noun/Object)** เช่น `Place Order`, `Withdraw Money`, `Deposit Money`, `Generate Report`, `Search Book`, `Login`
   - **ระดับความละเอียด:** ห้ามระบุถึง Action บนหน้าจอ UI เช่น "Click Button", "Input Name", "Validate Email" เพราะความละเอียดระดับนั้นจะอยู่ใน Activity Diagram
3. **System Boundary (ขอบเขตของระบบ):**
   - **สัญลักษณ์:** กรอบสี่เหลี่ยมผืนผ้า พร้อมชื่อระบบระบุไว้ด้านบน
   - **กฎตำแหน่ง:** **Actor ต้องอยู่นอกกรอบเสมอ** และ **Use Case ต้องอยู่ภายในกรอบเสมอ** ห้าม Use Case กระเด็นออกมานอกกรอบ
4. **Relationship (เส้นความสัมพันธ์):**
   - **Association (เส้นตรงทึบ):** เชื่อมระหว่าง Actor กับ Use Case ที่มีปฏิสัมพันธ์ด้วย
   - **Generalization (การสืบทอดคุณสมบัติ):** เส้นตรงมีหัวลูกศรสามเหลี่ยม ชี้จากประเภทย่อยไปยังประเภทหลัก (Parent-Child) เช่น `User` $\leftarrow$ `Student`, `Staff`, `Professor` หรือ `Vehicle` $\leftarrow$ `Auto`, `Tank`
   - **Include (`<<include>>`):** เส้นประลูกศรชี้จาก Base Use Case ไปยัง Included Use Case หมายถึง Base Use Case จะทำงานสำเร็จได้ **ต้องเรียกใช้อีก Use Case หนึ่งเสมอ (บังคับ 100%)** เช่น `Withdraw Money` $\rightarrow$ `<<include>>` $\rightarrow$ `Login / Authentication`
   - **Extend (`<<extend>>`):** เส้นประลูกศรชี้จาก Extended Use Case กลับมายัง Base Use Case หมายถึง พฤติกรรมเสริมที่จะ **เกิดขึ้นเฉพาะบางเงื่อนไขเท่านั้น (ไม่เกิดเป็นประจำ)** เช่น `Login` $\leftarrow$ `<<extend>>` $\leftarrow$ `Request OTP` (เมื่อใช้อุปกรณ์ใหม่) หรือ `Login` $\leftarrow$ `<<extend>>` $\leftarrow$ `Change Password` หรือ `Place Order` $\leftarrow$ `<<extend>>` $\leftarrow$ `Apply Discount` (เมื่อมีคูปอง)

## 3. จุดสำคัญที่อาจารย์เน้นย้ำ (Key Highlights)

1. **การแยกแยะระหว่าง `Include` กับ `Extend` (จุดที่นักศึกษาสับสนมากที่สุด):**
   - ถ้าฟังก์ชันย่อยต้องทำ **ทุกครั้ง ขาดไม่ได้** $\rightarrow$ ใช้ **`<<include>>`** (ลูกศรพุ่งออกจาก Base ไปหาตัวช่วย)
   - ถ้าฟังก์ชันย่อยทำ **เป็นบางครั้ง เมื่อเข้าเงื่อนไขเฉพาะ หรือเป็นทางเลือก** $\rightarrow$ ใช้ **`<<extend>>`** (ลูกศรพุ่งจากตัวเสริมกลับมาหา Base)
2. **Actor คนเดียวกันสามารถสวมได้หลายบทบาท:**
   - บุคคลจริง 1 คน สามารถเป็นทั้ง `Customer` และ `Technician` ในระบบตู้ ATM ได้
   - เจ้าหน้าที่ธุรการ (`Staff`) ที่ลงทะเบียนเรียน ป.โท ก็สามารถเป็น `Student` ในระบบ REG ได้ โดยระบบจะแยกแยะตามสิทธิ์ของ Role
3. **การสร้าง Use Case ต้องยึดจาก Requirement เสมอ:**
   - ห้ามมโนหรือเพิ่มฟังก์ชันเอง หากใน Requirement ไม่ได้ระบุว่ามีอาจารย์มายืมหนังสือ ก็ไม่ต้องใส่ Actor อาจารย์ในระบบห้องสมุด
4. **กรณีศึกษาในห้องเรียน: ระบบยืมคืนหนังสือห้องสมุด (Library System):**
   - **Actors:** `Student` (นักศึกษา), `Librarian` (บรรณารักษ์)
   - **Use Cases:** `Search Book`, `Borrow Book`, `Return Book`, `Check Member Status`, `Check Book Availability`, `Manage Book Data`
   - **ความสัมพันธ์ Include:** การ `Borrow Book` ต้อง `<<include>>` ทั้ง `Check Member Status` และ `Check Book Availability`

## 5. จุดที่แง้มว่าจะออกสอบ / แนวข้อสอบ (Exam Hints & Secrets)

1. **สัญลักษณ์และความหมายของความสัมพันธ์:**
   - ข้อสอบมักจะให้โจทย์สถานการณ์แล้วถามว่าเส้นเชื่อมระหว่าง Use Case A กับ B ต้องเป็น `<<include>>` หรือ `<<extend>>` พร้อมทิศทางของหัวลูกศร
   - **กับดักที่ต้องระวัง:** `Change Password` กับ `Login` ต้องเป็น `<<extend>>` ไม่ใช่ `<<include>>` เพราะไม่มีใครเปลี่ยนรหัสผ่านทุกครั้งที่ล็อกอิน
2. **การวาด Diagram ให้ถูกกฎเกณฑ์ทางวิศวกรรม:**
   - รูปร่าง Use Case ต้องเป็น **วงรี** เท่านั้น (ห้ามวาดวงกลมหรือสี่เหลี่ยม)
   - ชื่อ Use Case ต้องขึ้นต้นด้วย **คำกริยา (Verb)** เสมอ
   - Actor ต้องอยู่ **นอกกรอบ System Boundary** และ Use Case ต้องอยู่ **ในกรอบ** เท่านั้น
   - ห้ามมี Actor ลอยๆ ในอากาศโดยไม่มีเส้นเชื่อมต่อกับ Use Case อย่างน้อย 1 ฟังก์ชัน
3. **การแปลงข้อความ Requirement ออกมาเป็น Elements:**
   - ข้อสอบมักจะให้บทบรรยายระบบมา 1 ย่อหน้า แล้วให้นักศึกษาจำแนก:
     1. รายชื่อ Actor ทั้งหมด (ห้ามใส่ Database)
     2. รายชื่อ Use Case ทั้งหมด
     3. ระบุเงื่อนไข `<<include>>` ที่ซ่อนอยู่ในข้อความ (เช่น "ก่อนที่จะ... ระบบต้องตรวจสอบ...")
