## 2. สรุปสาระสำคัญ (Executive Summary)

### 2.1 กำเนิดและนิยามของ NoSQL (Not Only SQL)
- **NoSQL** ไม่ได้แปลว่า "ไม่มี SQL" แต่หมายถึง **"Not Only SQL"** ถูกพัฒนาขึ้นอย่างแพร่หลายช่วงก่อนปี 2010 เพื่อแก้ไขข้อจำกัดของฐานข้อมูลเชิงสัมพันธ์ (RDBMS) ที่ไม่สามารถรองรับการเติบโตแบบก้าวกระโดดของข้อมูลยุคใหม่ (Big Data) และระบบประมวลผลแบบกระจายศูนย์ (Distributed Systems)

### 2.2 ข้อจำกัดของ RDBMS เมื่อต้องสเกลบนระบบกระจายศูนย์ (Limitations of RDBMS)
1. **Join Are Expensive:** การ Join ข้าม Table บน Server เดียวทำได้เร็ว แต่หากกระจายข้อมูลไปเก็บคนละ Server (Distributed) การทำ Join ข้ามเครือข่ายจะกินทรัพยากรมหาศาลและช้ามาก
2. **Hard to Scale (Scale-Up vs Scale-Out):** RDBMS ถูกออกแบบมาเพื่อการขยายตัวในแนวตั้ง (**Vertical Scaling / Scale-Up**) บน Server เดี่ยวที่มีประสิทธิภาพสูง แต่การขยายในแนวนอน (**Horizontal Scaling / Scale-Out**) ข้ามหลายโหนดทำได้ยากยิ่ง
3. **Impedance Mismatch:** โปรแกรมมิ่งยุคปัจจุบันเป็นแบบ Object-Oriented (OO) แต่ RDBMS เก็บเป็นตาราง (Rows & Columns) ต้องมีการแปลงกลับไปกลับมา
4. **Expensive:** ค่าใช้จ่ายสูงทั้งค่า License, ฮาร์ดแวร์สเปกสูง และค่าจ้างผู้เชี่ยวชาญดูแลระบบ (Database Administrator - DBA)

### 2.3 นิยามและลักษณะของ Big Data (5 Vs)
- **Volume:** ข้อมูลมีปริมาณมหาศาล (ระดับ Terabyte ขึ้นไป)
- **Velocity:** ข้อมูลเกิดขึ้นและเปลี่ยนแปลงด้วยความเร็วสูงมาก
- **Variety:** ข้อมูลมีโครงสร้างที่หลากหลาย:
  - *Structured:* ข้อมูลมีโครงสร้างตารางชัดเจน (เหมาะกับ RDBMS)
  - *Semi-structured:* ข้อมูลกึ่งโครงสร้าง เช่น JSON, XML
  - *Unstructured:* ข้อมูลไร้โครงสร้าง เช่น ไฟล์เสียง, วิดีโอ, ภาพถ่าย, ข้อความแชต
- **Veracity:** ความถูกต้องและแม่นยำของข้อมูล
- **Value:** ข้อมูลต้องมีคุณค่าเชิงธุรกิจและนำไปใช้ประโยชน์ได้จริง

### 2.4 สี่โมเดลข้อมูลของ NoSQL (4 NoSQL Data Models)
| โมเดลข้อมูล (Data Model) | ลักษณะการจัดเก็บ | ตัวอย่างฐานข้อมูล | กรณีการใช้งานที่เหมาะสม |
| :--- | :--- | :--- | :--- |
| **1. Key-Value Store** | เก็บเป็นคู่ Key และ Value (Value คือก้อน Data ทั้งก้อน ไม่แยกคอลัมน์) | Amazon DynamoDB, Redis, Riak | Session ผู้ใช้, ตะกร้าสินค้าออนไลน์, Caching ที่ต้องการค้นหาด้วย Key อย่างรวดเร็ว |
| **2. Column Family / Wide-Column** | เก็บเป็น Row Key และ Column Family โดยแต่ละแถวไม่จำเป็นต้องมีคอลัมน์เหมือนกัน เขียนข้อมูลแบบ Append ต่อท้ายพร้อม Timestamp | Apache Cassandra, HBase | Time-series data, ข้อมูลสถิติ/Log ขนาดใหญ่ (>50GB) ซึ่ง Cassandra เขียนเร็วกว่า MySQL มหาศาล (0.12ms vs 300ms) |
| **3. Graph Database** | เก็บเป็น Node (โหนดข้อมูล), Edge/Relationship (เส้นความสัมพันธ์), และ Properties | Neo4j, InfiniteGraph, OrientDB | โครงข่าย Social Network (Facebook, LINE), แผนที่นำทาง (Route), ระบบแนะนำสินค้า, การสืบสวนรอยต่อการโกง/ติดตามโรคระบาด (Contact Tracing) |
| **4. Document-based Store** | เก็บเอกสารในรูปแบบ JSON / BSON / XML สามารถฝัง Array และ Nested Document ซ้อนกันได้หลายชั้น | MongoDB, CouchDB | โปรไฟล์ผู้ใช้, แค็ตตาล็อกสินค้า E-commerce, โพสต์ฟีดและคอมเมนต์ (ดึงข้อมูลแสดงผลทั้งหน้าได้ในคำสั่งเดียว) |

### 2.5 ทฤษฎีบทของบริวเวอร์ (CAP Theorem / Brewer's Theorem)
ในระบบฐานข้อมูลแบบกระจายศูนย์ (Distributed Database) จะสามารถรับประกันคุณสมบัติได้**อย่างมากที่สุดเพียง 2 จาก 3 ข้อพร้อมกัน** ดังนี้:
1. **Consistency (C):** ข้อมูลทุกโหนดต้องถูกต้องตรงกันและมองเห็นตรงกันในเวลาเดียวกัน
2. **Availability (A):** ระบบต้องพร้อมให้บริการและตอบสนองการอ่าน/เขียนตลอดเวลา แม้บางโหนดจะล่ม
3. **Partition Tolerance (P):** ระบบยังคงทำงานได้ต่อเนื่องแม้เครือข่ายระหว่างโหนดจะขาดการเชื่อมต่อ (Network Partition)

**การเลือกคู่ตาม CAP Theorem:**
- **CA (Consistency + Availability):** **RDBMS ดั้งเดิม (Oracle, MySQL)** (ไม่เน้น Partition ข้ามเครื่อง)
- **CP (Consistency + Partition Tolerance):** **MongoDB, HBase** (ยอมปิดกั้นการตอบสนองชั่วคราวเพื่อรักษาความถูกต้องของข้อมูล)
- **AP (Availability + Partition Tolerance):** **Apache Cassandra, CouchDB, DynamoDB** (ยอมให้ข้อมูลยังไม่อัปเดตทันทีแบบ Eventual Consistency เพื่อให้ระบบตอบสนองได้ตลอดเวลา)

## 3. จุดสำคัญที่อาจารย์เน้นย้ำ (Key Highlights)

1. **เมื่อใดต้องเลือกใช้ RDBMS และเมื่อใดควรเลือก NoSQL:**
   - **ใช้ RDBMS:** เมื่องานเกี่ยวข้องกับ **ข้อมูลทางการเงิน (Financial Data), ข้อมูลธุรกิจสำคัญ (Business-critical Data)** ที่ต้องการความถูกต้องแม่นยำสูงลิ่ว และต้องการคุณสมบัติ **ACID Properties 100%**
   - **ใช้ NoSQL:** เมื่องานเกี่ยวข้องกับ **Big Data, ข้อมูลที่มีความซับซ้อนหลากหลาย (Semi/Unstructured), โครงข่ายเครือข่าย (Social Network), หรือระบบที่ต้องการขยายตัวสูงแบบ Horizontal Scaling บน Cloud**
2. **การตั้งชื่อ Foreign Key ให้สื่อความหมาย:**
   - ใน RDBMS หากตาราง `Dog` มี PK คือ `id` เมื่อนำไปเป็น FK ในตาราง `Bark` และ `Comment` ควรตั้งชื่อเป็น `dog_id` เพื่อไม่ให้ชื่อ Attribute ซ้ำกันและสื่อถึงความเชื่อมโยงที่ชัดเจน
3. **กลไกการเขียนข้อมูลของ Cassandra:**
   - ใช้หลักการ **Append-only** ต่อท้ายไฟล์พร้อม Timestamp จึงเขียนได้เร็วมาก (0.12 ms) ไม่ต้อง Overwrite ทับข้อมูลเดิม และจะมีระบบ Background Garbage Collection มาเก็บกวาดข้อมูลเก่าในภายหลัง
